읽는 법

  • 절차는 앱 중립 — 본문은 어떤 앱에도 적용된다. Diem에서 실제로 넣은 값은 각 STEP 끝의 [예시: Diem] 한 줄과 배포 기록에만 있다. 그대로 복사하지 말고 자기 앱 값으로 치환할 것
  • 화면이 문서보다 옳다 — Google이 콘솔 UI를 자주 바꾼다. 메뉴 명칭이 다르면 캡처를 기준으로 같은 뜻의 항목을 찾고, 이 문서에 없는 화면이 나오면 캡처해 두었다가 이 매뉴얼에 반영한다
  • 작은 썸네일(가로 스크롤 줄)은 클릭하면 새 탭에 원본 크기로 열린다

STEP 0. 사전 준비 실측 완료

콘솔에 들어가기 전에 끝낸다 — 하나라도 없으면 중간에 멈춘다

  1. keystore 생성·백업 + 서명된 AAB

    업로드 키는 오프사이트 포함 2곳 이상 백업, 비밀번호는 키 파일과 다른 곳(비밀번호 관리자)에 — Play 앱 서명 덕에 재설정은 가능하지만 첫 업로드 전 구간이 가장 위험하다. bundleRelease로 AAB(Android App Bundle — Play에 올리는 빌드 파일)를 만든 뒤 jarsigner -verify로 "jar verified"를 확인하고, 유닛 테스트 전체 통과가 선행 조건.

  2. 개인정보처리방침 URL 호스팅

    GitHub Pages로 충분. 조건: HTTPS · 로그인 없이 접근 · 자리표시자([연락 이메일] 등) 0건. 연락처는 [공개 연락용 회사 이메일]로 — 스토어·심사에 공개된다.

  3. 스토어 자산

    아이콘 512×512 PNG · 피처 그래픽 1024×500 · 폰 스크린샷 1080×2160(2:1) 최소 2장.

  4. 개발자 계정 — 조직 계정 권장 계정 "확인됨" + 전화번호 인증 전에는 "첫 번째 앱 만들기"가 비활성

    "테스터 12명 × 연속 14일" 비공개 테스트 의무는 2023-11-13 이후 생성된 개인 계정 전용이라 조직 계정(DUNS 등록)은 면제. 계정 유형부터 확인한다.

  5. 앱 콘텐츠 12항목 답안 사전 결정

    선언은 빌드 실제와 일치해야 한다(STEP 2). [광고 없음] 빌드면 병합 매니페스트에서 AD_ID·ADSERVICES 권한 0건을 미리 확인한다.

공개 리포에 올릴 문서·코드는 커밋 전 저자를 확인한다. git log -1 --format='%an %ae'로 확인 — 전역 기본값이 개인 이메일이면 공개 히스토리에 영구 노출된다(함정 8).

실측: Diem → 배포 기록 0절

STEP 1. 앱 만들기 실측 완료

홈 › 앱 만들기 · 여기서 정한 값은 대부분 되돌릴 수 없다

  1. 앱 이름

    30자 이내. 스토어 등록정보에서 나중에 수정 가능.

  2. 기본 언어

    전 세계 기본 노출 언어. 나머지 언어는 스토어 등록정보에서 번역으로 추가한다.

  3. 앱 또는 게임 · 무료 또는 유료 무료 → 유료 전환은 영구 불가

    앱/게임을 잘못 고르면 IARC 설문이 통째로 달라진다. 유료 → 무료는 가능.

  4. 선언 2개

    개발자 프로그램 정책 + 미국 수출법, 둘 다 체크.

  5. 만들기

    생성 직후 대시보드에 "할 일" 목록이 펼쳐진다 — 이 문서의 STEP 2~4 순서와 같다.

실측 — 패키지 이름 입력란이 이 폼에 존재한다. 구 문서에는 없던 항목(과거엔 첫 AAB 업로드 시점에 확정). 입력 후 [사용 가능 여부 확인]을 클릭하고, 값은 빌드의 applicationId와 일치해야 하며 생성 후 변경할 수 없다.

실측: Diem – D-Day Countdown Widget(29/30) · en-US · 앱 · 무료 → 배포 기록 1절

STEP 2. 앱 콘텐츠 12항목 실측 완료

정책 및 프로그램 › 앱 콘텐츠 · 심사 제출의 관문, 전부 수동 입력

위에서 아래로 순서대로. 선언은 빌드 실제와 일치해야 한다 — "광고 없음" 선언인데 병합 매니페스트에 AD_ID 권한이 남아 있으면 업로드가 거부된다. 광고 SDK가 의존성에 남아 있으면 매니페스트 병합으로 AD_ID 계열 권한 4종이 자동 삽입되므로 tools:node="remove"로 제거하고 재빌드 때마다 병합 매니페스트에서 AD_ID·ADSERVICES 0건을 확인한다. 목록에 없는 항목이 새로 보이면 해당 기능을 안 쓰는 한 "해당 없음/아니요"로 답한다.

항목요지[광고 없음][광고 있음]
1 개인정보처리방침호스팅해 둔 HTTPS URL 입력. 언제든 교체 가능URL 입력동일 (수집 항목 반영판)
2 앱 액세스 권한로그인·잠금 기능 유무로그인 없으면 "모든 기능 제한 없음"
3 광고광고 SDK 실탑재 여부와 일치시킬 것아니요예
4 콘텐츠 등급 (IARC)카테고리 "다른 모든 앱 유형" 선택 후 설문. 이메일은 [공개 연락용 회사 이메일]전 문항 "아니요" → 전체이용가 (기능상 해당 없을 때)
5 타겟층전 연령 체크 금지 — 12세 이하 포함 시 가족 정책 심사가 통째로 붙는다"만 18세 이상" 단독 권장 (스토어 노출 영향 없음)
6 뉴스 앱뉴스 서비스 여부아니요
7 코로나19 앱접촉자 추적·이력 여부해당 없음
8 데이터 보안14개 데이터 유형별 수집·공유. 기기 밖으로 안 나가면 "수집" 아님수집 안 함광고 SDK가 수집하는 유형(기기 ID 등) 공개
9 정부 앱정부 기관 대행 여부아니요
10 금융 기능대출·투자·송금 등제공하지 않음
11 건강 앱건강 데이터·의료기기 (항목 자체가 안 보일 수 있음)아니요
12 광고 ID병합 매니페스트의 AD_ID 권한과 일치해야 함아니요 — AD_ID 권한 제거 필수예
타겟층에서 전 연령을 체크하지 않는다. 12세 이하를 포함하면 가족 정책 심사가 통째로 붙는다. "만 18세 이상" 단독 선택이 스토어 노출·검색에 영향을 주지 않는다(함정 6).

실측: Diem [광고 없음] 열 그대로 · 타겟층 만 18세 이상 단독 → 배포 기록 2절

STEP 3. 스토어 등록정보 실측 완료

사용자 늘리기(성장) › 스토어 현황 › 기본 스토어 등록정보

  1. 글자수 한도 — 제목 30 · 간단한 설명 80 · 자세한 설명 4,000

    입력 전에 실측해 둔다. 콘솔에서 즉석 수정하면 검증된 글자수·키워드가 깨진다.

  2. 확정 문구를 복붙용 .txt로 추출

    리스팅 문서(PLAY_LISTING.md)의 확정 블록을 그대로 붙여넣는다.

  3. 그래픽 업로드

    아이콘 · 피처 그래픽 · 스크린샷을 파일명 번호 순서대로.

  4. 언어 — 기본 언어 + 전략상 필요한 번역만

    "AI로 번역 가져오기"는 쓰지 않는다 — 준비한 문구가 검색 키워드를 반영한다. 나머지 언어는 유입이 생기면 그때 추가(재심사 불필요).

캡처는 다음 앱 배포 시 촬영해 추가한다.

실측: Diem 제목 29/30 · 간단한 설명 73/80 · 자세한 설명 2,185/4,000 · en + ko → 배포 기록 3절

STEP 4. 내부 테스트 실측 완료

테스트 및 출시 › 테스트 › 내부 테스트 · 심사 없이 즉시 게시되는 유일한 트랙

  1. 테스터 이메일 목록 만들기

    테스터 탭 › 목록 이름 + 테스터의 Google 계정 이메일 › 저장.

  2. 새 버전 만들기 › AAB 업로드 드래그 업로드는 1단계(업로드 영역)에서만

    첫 업로드 시 Play 앱 서명이 자동 등록된다.

  3. 출시 노트

    <en-US> 블록 형식으로 입력(화면 안내 따름). 추가 언어는 <ko-KR> 등 블록 추가.

  4. 출시 › 즉시 게시

    내부 테스트는 심사 없이 수 분 내 반영.

  5. 옵트인 링크로 실기기 설치

    테스터 탭의 참여 링크를 테스터에게 전달 › "테스터 되기" 수락 후 Play 스토어에서 설치(사이드로드 아님) › 핵심 기능 5분 점검. 심사 전에는 앱명 뒤 "(unreviewed)"·회색 아이콘·17+ 배지가 정상(함정 4).

실측 — 드래그 업로드는 릴리스 마법사 1단계(업로드 영역)에서만 동작한다. 2단계(미리보기)로 넘어간 상태에서 드래그하면 아무 반응이 없다(08-13 실측 사고 — 1단계로 돌아가 해결).

실측: Diem 번들 3(1.2.0) 08-13 게시 · 테스터 5명 → 배포 기록 5절

STEP 5. 비공개(Closed) 테스트 실측 완료

테스트 및 출시 › 테스트 › 비공개 테스트 · 첫 심사가 붙는 트랙

  1. 테스터 목록 지정

    테스터 탭에서 이메일 목록 선택·저장. "게시 개요로 이동하시겠어요?" 팝업은 나중에 — 릴리스 작업을 먼저 끝낸다.

  2. 라이브러리에서 App Bundle 추가 같은 versionCode는 재업로드 불가 — 재빌드 금지

    내부 테스트에 올린 검증된 번들을 "라이브러리에서 추가"로 선택한다. versionCode(빌드마다 1씩 올리는 정수 — Play는 같은 값을 두 번 받지 않는다)가 같은 파일은 다시 업로드할 수 없다.

  3. 출시명 자동 입력 + 출시 노트 "이전 버전에서 복사"

    소스 트랙/버전 선택 › "노트 복사" — 등록된 언어가 번역 포함 한 번에 넘어온다.

  4. 미리보기 — 경고 확인

    "네이티브 디버그 기호 미업로드"는 제출 비차단(Kotlin 앱 통상 무시 가능). 광고 ID 불일치·서명 경고가 뜨면 그 자리에서 해결.

  5. 게시 개요 › "변경사항 검토 제출"

    제출 후 "검토 중인 변경사항" 표시를 확인한다. 사전 검사 최대 ~14분 → 심사(통상 7일 이내).

"출시 시작" 클릭만으로는 제출되지 않는다. 게시 개요에서 "변경사항 검토 제출"까지 눌러야 심사가 시작된다 — 이 최종 제출 누락으로 5일을 허비한 실사고(08-13). 제출 후 게시 개요에 "검토 중인 변경사항"이 없으면 미제출이다(함정 1).

실측: Diem 번들 3(1.2.0) · 테스터 5명 · 08-18 09:31 제출 → 09:44 승인(13분 — 1회 실측, 일반화 금지) → 배포 기록 5.5절

↑ 8단계 한눈에

STEP 6. 프로덕션 제출 완료·승인 대기

테스트 및 출시 › 프로덕션 · 첫 공개 트랙 — 여기서의 선택 일부는 되돌릴 수 없다

  1. 국가/지역 선택 트랙별 독립 — 프로덕션은 0개에서 시작

    국가/지역 탭 › 추가 › 선택 › 저장 › "게시 개요로 이동?" 확인 모달은 "나중에". 제외 국가(EEA 등)는 앱별 정책 판단을 선택 전에 끝낸다.

  2. 새 버전 만들기 › AAB 업로드

    새 versionCode 파일을 업로드하거나, 테스트를 통과한 번들을 "라이브러리에서 추가"로 승격한다. 업로드 화면 ⓘ — "앱 서명 키 선택은 공개 트랙 게시 후 고정"(비가역).

  3. 출시명 자동 입력 · 출시 노트 "이전 버전에서 복사"

    소스 트랙/버전 선택 › 노트 복사 — 등록 언어가 한 번에 넘어온다.

  4. 다음 › 미리보기 — 경고 펼쳐 확인 첫 프로덕션은 단계적 출시 비율 UI 없음 — 100%

    "네이티브 디버그 기호 미업로드"는 네이티브 코드 없는 앱에선 해소 불가·비차단. 저장 › "게시 개요로 이동?" 대화상자.

  5. 게시 개요 › "검토를 위해 변경사항 N개 제출"

    확인 모달(통상 7일 이내) › "검토 중인 변경사항" + 빠른 검사(최대 14분). 제출 활동 페이지에서 ID·시각·상태를 확인한다.

앱 서명 키 선택은 공개 트랙 게시 후 고정된다(비가역). 업로드 화면 ⓘ가 명시한다. 프로덕션이 첫 공개 트랙이면 지금이 마지막 선택 지점 — 키 정책을 정하지 않았다면 업로드 전에 멈춘다(함정 11).

실측: Diem 4(1.2.1) 2026-08-21 14:23 제출·검토 중 → 배포 기록 6절

STEP 7. 심사 후 일부 실측(프로덕션 승인 대기)

비공개 테스트 승인(08-18)에서 실측한 것 + 프로덕션 승인 시 같은 절차

  1. 승인 알림

    메일 "새 게시 사항"은 작업 요청이 아닐 수 있다("앱 업데이트가 게시되었습니다" = 게시 완료 알림). 게시 개요에 대기 변경 0건이면 할 일은 끝. 대기 중에는 새 버전 제출 금지 — 대기열 뒤로 밀린다.

  2. 승인 ≠ 게시 관리형 게시 ON이면

    관리형 게시(승인과 실제 노출을 분리하는 콘솔 설정 — 게시 개요에서 확인)가 켜져 있으면 게시 개요 › "관리형 게시가 사용 설정됨" › 변경사항 게시를 눌러야 사용자에게 보인다.

  3. 스토어 노출 확인 + 실기기 스모크

    게시 후 수 시간 내 스토어 검색·설치·스크린샷 표시를 확인하고, 실기기에서 핵심 기능(날짜 선택기·위젯 등)을 점검한다. 테스트 트랙은 옵트인 링크를 배포해야 설치가 시작된다.

  4. "다음 출시 버전을 위한 발견 항목"

    사용자 환경 카테고리·비차단으로 콘솔에 뜰 수 있다. 현재 릴리스는 그대로 두고 다음 versionCode에서 수정한다.

  5. 문제 시 출시 중단, 반려 시 부록 A

    프로덕션 › 출시 관리 › 출시 중단(halt) → 수정 후 다음 versionCode. 반려는 사유 메일 캡처 → 각 앱 PLAY_RELEASE_GUIDE 부록 A(반려 유형별 대응표) 기준으로 수정·재제출.

관리형 게시 — 승인 메일이 와도 스토어에 안 보인다. 관리형 게시가 켜진 계정은 승인과 게시가 분리돼 있다. "변경사항 게시"를 누른 뒤 대기 변경 0건을 확인한다(함정 9).
